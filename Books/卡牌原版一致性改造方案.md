# 卡牌原版一致性改造方案

## 1. 背景

当前项目已经通过 `carnival_performer.xlsx` 配置了 150 张原版小丑牌，并且所有卡牌 ID
均能在运行时代码中找到对应引用。但现有实现将卡牌逻辑分散在计分、回合生命周期、
商店和盲注等多个控制器中，缺少统一的触发顺序和状态传播机制。

现有 Unity EditMode 测试共 8 条，其中只有“幻觉”和“零糖可乐”属于小丑牌专项行为测试。
静态审计已确认至少 26 张小丑牌存在行为偏差，另有 36 张已锁定的罕见或稀有小丑牌
缺少正常解锁和获取路径。

本方案的目标不是继续为单张卡牌增加临时判断，而是建立可覆盖全部 150 张小丑牌的
统一运行时规则，使 Excel 负责配置数据，Core 层负责执行游戏规则。

## 2. 改造目标

1. 150 张小丑牌的触发时机、数值变化和组合行为与原版一致。
2. 所有卡牌效果通过统一的生命周期入口执行。
3. 蓝图和头脑风暴可以复制所有被标记为兼容的触发阶段。
4. 卡牌销毁、出售、复制、版本、贴纸和解锁状态具有统一模型。
5. Excel 继续保存名称、说明、参数及兼容性，不在 UI 层实现具体规则。
6. 每张小丑牌至少拥有一条独立行为测试，关键组合拥有交互测试。

## 3. 现有问题

### 3.1 触发阶段分散

小丑牌效果目前主要分布在以下文件中：

- `CarnivalPokerGame.BalatroScoring.cs`
- `CarnivalPokerGame.BalatroLifecycle.cs`
- `CarnivalPokerGame.Shop.cs`
- `CarnivalPokerGame.Boosters.cs`
- `CarnivalPokerGame.Tags.cs`

不同文件分别修改计分结果和卡牌状态，无法保证原版要求的执行顺序。例如跑步选手、
方形小丑和备用裤子的成长发生在本手计分结束后，导致新获得的数值晚一手生效。

### 3.2 运行时模型不足

`CarnivalConsumable` 目前是只读配置对象，没有独立的运行时实例、版本和售价。因此：

- 帕奇欧只能重复添加同一个消耗牌对象，无法创建负片副本。
- 礼品卡不能提高消耗牌售价。
- 篝火不能监听消耗牌出售。
- 马戏团长不能正确控制塔罗、星球和幻灵牌的重复出现。

### 3.3 缺少统一事件

卡牌销毁、出售、使用消耗牌等行为没有统一事件入口，导致卡尼奥、星座等牌虽然拥有
状态字段和计分分支，却没有任何地方更新状态。

### 3.4 测试覆盖不足

现有测试主要覆盖目录数量、盲注基础流程和两张小丑牌，不能证明其余卡牌的实际效果。
随机效果、重触发、复制、Boss 禁用和卡牌版本都缺少专项测试。

## 4. 目标架构

所有具体游戏规则继续位于：

`Assets/GameScripts/HotFix/GameLogic/Core/`

UI、配置加载和框架适配层不得直接修改卡牌状态。跨越 Core 边界的命令与状态通知仍由
`CarnivalSystem` 统一接收和发布。

### 4.1 小丑牌触发类型

新增统一触发类型：

```csharp
public enum CarnivalJokerTrigger
{
    BlindSelected,
    BeforeHandScored,
    CardScored,
    CardHeld,
    AfterHandScored,
    CardDiscarded,
    CardDestroyed,
    PlayingCardAdded,
    ConsumableUsed,
    CardSold,
    BoosterOpened,
    BoosterSkipped,
    RoundEnded,
    ShopEnded,
}
```

触发类型表示原版卡牌所处的计算阶段，不能用 UI 操作名称替代游戏规则阶段。

### 4.2 统一触发上下文

新增 `CarnivalJokerContext`，根据触发阶段携带本次计算需要的数据：

```csharp
public sealed class CarnivalJokerContext
{
    public CarnivalJokerTrigger Trigger { get; init; }
    public CarnivalScoreResult ScoreResult { get; init; }
    public IReadOnlyList<CarnivalCard> PlayedCards { get; init; }
    public CarnivalCard CurrentCard { get; init; }
    public CarnivalCard DestroyedCard { get; init; }
    public CarnivalDestroyReason DestroyReason { get; init; }
    public CarnivalConsumableState Consumable { get; init; }
    public CarnivalPerformerState SoldJoker { get; init; }
    public bool IsCopiedEffect { get; init; }
}
```

上下文只传递本次规则计算所需的数据，不暴露 Ctrl 或 Model 引用给 Core 外部。

### 4.3 统一执行入口

新增：

```csharp
private void ApplyJokers(
    CarnivalJokerTrigger trigger,
    CarnivalJokerContext context)
```

该方法按照小丑牌从左到右的顺序执行。单张牌的效果由独立处理器或按触发阶段拆分的
方法执行，不再让不同流程直接操作特定小丑牌状态。

推荐执行顺序：

```text
识别牌型和计分牌
→ BeforeHandScored
→ 逐张 CardScored 及重触发
→ CardHeld
→ 小丑牌独立筹码和倍率
→ AfterHandScored
→ 处理碎裂和销毁
→ 补牌
```

## 5. 关键系统改造

### 5.1 蓝图与头脑风暴

当前复制逻辑只调用独立计分阶段，不能复制计分牌、留手牌、选择盲注、弃牌和商店阶段。

应改为在每个触发阶段转发当前上下文：

```csharp
ExecuteJoker(
    target,
    context,
    copiedBy: blueprint,
    copyDepth: copyDepth + 1);
```

规则要求：

1. 只复制目标小丑牌的能力，不复制目标的版本效果。
2. 复制牌自身的闪箔、镭射或多彩版本正常参与计分。
3. 检查配置中的 `blueprint_compatible`。
4. 使用访问链或最大深度避免循环复制。
5. 成长状态属于实际目标牌，不为复制牌创建重复状态。
6. 不兼容牌在任何触发阶段都不能被复制。

### 5.2 卡牌销毁

增加唯一入口：

```csharp
private bool DestroyPlayingCard(
    int cardId,
    CarnivalDestroyReason reason)
```

该方法负责：

1. 从牌库、手牌、弃牌堆和选中集合中移除卡牌。
2. 发布 `CardDestroyed` 触发。
3. 卡尼奥在被销毁牌为人头牌时成长。
4. 玻璃小丑在玻璃牌被销毁时成长。
5. 避免同一张牌被重复销毁或重复触发。
6. 在重触发过程中重新读取最新卡牌状态。

徒步者和吸血鬼不能一直使用触发循环开始前的旧 `CarnivalCard` 对象，否则会出现永久
筹码覆盖或增强状态被重复移除的问题。

### 5.3 消耗牌运行时实例

保留 `CarnivalConsumable` 作为配置定义，新增：

```csharp
public sealed class CarnivalConsumableState
{
    public CarnivalConsumable Content { get; }
    public CarnivalCardEdition Edition { get; set; }
    public int SellValue { get; set; }
}
```

将 `_consumables` 改为 `List<CarnivalConsumableState>`，并增加：

- 购买、使用和出售消耗牌接口。
- 负片消耗牌不占普通消耗牌槽位。
- 创建副本时生成新的运行时对象。
- 礼品卡同时增加小丑牌和消耗牌售价。
- 篝火监听所有卡牌出售。
- 帕奇欧创建独立的负片消耗牌副本。
- 马戏团长统一控制小丑牌和消耗牌的重复限制。

### 5.4 Boss 盲注规则

所有 Boss 效果必须通过统一查询：

```csharp
private bool IsBossRuleActive(CarnivalBossRule rule)
```

出牌数量限制、基础分减半、人头牌削弱和减少弃牌次数都不得直接读取
`CurrentBlind.BossRule`。

摔跤手出售或希科生效后，所有调用点都应得到 `false`。斗牛士则通过本手上下文中的
`TriggeredBossRule` 判断是否奖励金币。

### 5.5 牌型识别与计分牌集合

牌型计算器应同时返回：

```csharp
public readonly struct CarnivalHandEvaluation
{
    public CarnivalHandKind Kind { get; init; }
    public IReadOnlyList<int> ScoringCardIds { get; init; }
}
```

必须满足：

- 石头牌不参与点数、花色和牌型组合，但可以作为计分牌提供石头筹码。
- 四指允许四张组成顺子或同花，第五张无关牌不能自动计分。
- 万能牌正确参与同花、花盆和重影的花色条件。
- 顺子支持 A2345。
- 捷径允许相邻牌之间跳过一个点数。
- 偶像从当前完整牌组实际存在的牌中选择目标。

### 5.6 解锁与获取

新增局外解锁状态接口，例如：

```csharp
public interface ICarnivalUnlockModel
{
    bool IsJokerUnlocked(string jokerId);
    void UnlockJoker(string jokerId);
}
```

商店候选池使用：

```csharp
performer.UnlockedByDefault ||
unlockModel.IsJokerUnlocked(performer.Id)
```

每条 `unlock_requirement` 应对应明确的 Core 层统计数据和解锁条件。传奇牌仍由灵魂牌
生成，乌合之众只能生成符合原版解锁规则的普通小丑牌。

## 6. 已知偏差修复映射

| 分类 | 小丑牌 | 修复方式 |
|---|---|---|
| 状态没有增长 | 星座 | 在 `ConsumableUsed` 且类型为星球牌时增加 ×0.1 |
| 状态没有增长 | 卡尼奥 | 在 `CardDestroyed` 且为人头牌时增加 ×1 |
| 复制不完整 | 蓝图、头脑风暴 | 复制完整触发管线，不只复制独立计分 |
| 消耗牌模型不足 | 礼品卡、篝火、帕奇欧 | 增加消耗牌运行时状态、售价、版本和出售事件 |
| 重复控制不完整 | 马戏团长 | 对小丑、塔罗、星球、幻灵统一执行重复检查 |
| Boss 禁用不完整 | 摔跤手、希科 | 所有 Boss 判断统一调用 `IsBossRuleActive` |
| 重触发状态错误 | 徒步者、吸血鬼 | 每次重触发重新读取当前卡牌实例 |
| 效果耗尽未自毁 | 苏打水、黑龟豆、冰淇淋、拉面 | 在对应计数到达原版下限时销毁 |
| 成长晚一手 | 跑步选手、方形小丑、备用裤子 | 移到 `BeforeHandScored` |
| 重置晚一手 | 搭乘巴士、绿色小丑、方尖石塔 | 在独立倍率计算前更新或重置状态 |
| 牌型与计分牌错误 | 四指 | 返回实际组成顺子或同花的四张计分牌 |
| 概率遗漏 | 六六大顺 | 所有列明概率统一经过概率服务，包括玻璃牌碎裂 |
| 目标选择错误 | 偶像 | 从完整牌组当前存在的牌中选择点数和花色 |
| 万能牌交互 | 重影 | 使用花色集合判断梅花与其他花色，支持万能牌 |

## 7. Excel 配置职责

`Configs/GameConfig/Datas/carnival_performer.xlsx` 继续保存：

- ID、名称、说明、价格和稀有度。
- 原版触发阶段和效果类别。
- 蓝图、易腐和永恒兼容性。
- 原版数值参数。
- 默认解锁状态及解锁说明。

复杂流程不能完全依靠字符串参数描述。Excel 决定“数值和兼容性”，Core 代码决定
“触发顺序和状态变化”。修改配置后执行：

```bash
cd Configs/GameConfig
./gen_code_bin_to_project.sh
```

禁止直接修改 Luban 生成文件。

## 8. 测试方案

### 8.1 单牌测试

为 150 张小丑牌分别建立至少一条行为测试。测试名称使用：

```text
Joker_<Id>_<Trigger>_<ExpectedBehavior>
```

每条测试必须验证实际结果，而不是只验证卡牌 ID 存在。

### 8.2 通用规则测试

至少覆盖：

1. 计分阶段顺序。
2. 小丑牌从左到右的执行顺序。
3. 蓝图和头脑风暴的可复制与不可复制牌。
4. 红蜡封、黄昏、烂脱口秀演员、喜与悲等重触发叠加。
5. 石头牌、万能牌、四指和捷径的牌型识别。
6. Boss 禁用后的所有规则入口。
7. 卡牌销毁只触发一次。
8. 负片消耗牌和负片小丑牌的槽位计算。
9. 锁定牌不能进入普通商店候选池。
10. 固定随机种子下的概率效果。

### 8.3 测试辅助接口

在 EditMode 测试程序集内提供构造游戏局面的辅助器，避免每条测试通过随机商店获取卡牌：

```csharp
CarnivalGameTestBuilder
    .WithJoker("runner")
    .WithHand(...)
    .WithMoney(10)
    .WithBlind(...)
    .Build();
```

辅助器仅用于测试，不应暴露为正式游戏接口。

## 9. 实施阶段

### 第一阶段：规则基础

1. 增加触发枚举和上下文。
2. 建立统一执行入口。
3. 调整计分阶段顺序。
4. 集中卡牌销毁。
5. 修复 Boss 规则查询。

完成标准：现有测试全部通过，新增基础阶段顺序测试通过。

### 第二阶段：运行时模型

1. 增加消耗牌运行时状态。
2. 增加消耗牌出售。
3. 统一卡牌版本和槽位规则。
4. 重做蓝图与头脑风暴复制。

完成标准：复制、帕奇欧、礼品卡、篝火和马戏团长测试通过。

### 第三阶段：逐牌修复

按照本方案的已知偏差表逐张修复，并补充对应测试。修复时不得只调整测试期望值，
必须以 Excel 中的原版说明和参数为依据。

完成标准：26 张已知偏差牌专项测试全部通过。

### 第四阶段：解锁与完整回归

1. 实现 45 张非默认解锁牌的解锁条件。
2. 完成 150 张单牌测试。
3. 增加关键组合和随机效果测试。
4. 在 Unity Editor 中执行完整 EditMode 和 PlayMode 回归。

## 10. 验收标准

只有同时满足以下条件，才能认定 150 张小丑牌功能正常：

- Excel 中存在 150 个唯一小丑牌 ID。
- Luban 生成和 GameLogic 编译无错误。
- Unity Console 无新增错误。
- 150 张单牌行为测试全部通过。
- 蓝图、头脑风暴、重触发、Boss、版本和消耗牌组合测试全部通过。
- 45 张非默认解锁牌均具有可验证的解锁或传奇生成路径。
- 不存在 UI 或 Core 外部代码直接修改游戏状态。
- 在固定随机种子下，概率效果结果可重复验证。

在上述条件完成前，“代码中存在对应 ID”或“目录数量为 150”都不能作为功能正常的依据。
